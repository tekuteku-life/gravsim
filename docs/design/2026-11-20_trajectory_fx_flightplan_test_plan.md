## 1. 方針

1. **期待値の出典**: 期待値は設計書の式・表・保証から導く。実装の現在の出力をそのまま期待値にしない。設計書に数値がない項目（例: 演出の色）は、設計書の契約（真偽・範囲・順序）だけを確かめる。
2. **3 観点**: 各テスト対象について、正常系（標準の使い方）、異常系（`null`/`undefined`/`NaN`/負値/文字列/範囲外/状態不整合/存在しない対象）、境界値（しきい値の直前・一致・直後、0、最大値、空・単一・多段）を含める。
3. **実経路**: 予測とプリセットは、アプリと同じ経路（`ObjectPlacer` → `PresetManager.applyToLauncher` → `RocketLauncher.updatePredictionSync()`／`rollout()`）でも確かめる。描画は実物の `TrajectoryPredictor.renderTrajectory`・`RocketRenderer` を記録用のモック ctx で呼んで、描かれた座標で判定する。
4. **決定性**: 乱数（`updatePressure` のノイズなど）に依存する値は期待値にしない。予測結果の `hostId`・`domId` はオブジェクトの生成順で変わるため、黄金値と比べる場合は除外する（Gate 2 Iteration 9 Watchpoint 2）。
5. **実行時間**: 既定の `npm test` 全体で数分以内に収める。1 ファイルあたり 60 秒以内を目安とし、重い組合せ（5 ワールド × 8 方位 × 全期間）は代表構成に絞る。同期ブロック時間の受入基準（§4.12）は計測のばらつきが大きいため既定のテストに入れず、§4.12 の方法で測る計測スクリプトを `testsuites/perf/` に置く（`npm test` には含めない）。
6. **本体コードは変更しない**: テストで本体の不具合が見つかった場合は、本体を直さずに作業者へ報告し、工程 2 へ差し戻すかを判断する。

## 3. 単位ごとの必須項目

### A. 自転角・バッファ・同期
- `BUFFER_INDEX`（47〜50）・`OBJ_ATTR_COUNT = 51`・`ROCKET_FLAG`（bit 16〜19）・`STAGE_STATE_TO_CODE`／`CODE_TO_STAGE_STATE` の値と相互変換。`parseWorkerToMain` はコードを `Math.round` してから引くため、小数は最も近い状態になり、範囲外・`NaN` は `'PRE_LAUNCH'`（設計書 §3.1.1-1）。
- `WorkerBridge.formatWorkerToMain`／`parseWorkerToMain`: 天体・ロケット・デブリのそれぞれでスロット 47〜50 が毎回明示的に上書きされる（同じバッファを別種のオブジェクトで再利用しても前の値が残らない）。RCS フラグ・`hasPayloadPropulsion` の往復。
- 自転角の積分: `ROTATION_PERIOD` が正・負・0・`NaN`・`1e-6` 前後で、`rotationAngle` の増分が設計式どおり（0・`NaN` では変化しない）。`addObject`／`updateObject` での `rotationAngle`・`rotationPeriod` の反映と、非有限値の無視。
- ホールドダウン: ステップ後の位置・速度が `host.v ± ω × r` と一致する（サブステップ数によらない）。ホールドダウン中のロケットは重力・推力で動かない。解除後は通常の積分。予測エンジンでも同じ。
- `ObjectManager.updateObjectParams` の 2 パス: 履歴更新（Pass 2A）が破壊処理（Pass 2B）より前に全対象で行われる。新規生成はデブリだけ。`_applyBaseState`／`_applyRocketState` のガード（`rotationAngle`・`mach`・`stageState`・`stgTimer`・RCS が欠けている・非有限のときは上書きしない）。
- `Rocket._recordActualFlightPath`: 最新点が間引かれない。記録に `time` が付く。切替時刻の前は地表固定系、後は慣性系の移動量で記録を判定する（静止軌道でも記録が止まらない、G2-3-03）。
- 主スレッドに自転角の独自積分がない（`Universe` と `PadEffectRenderer`、G2-09）。`PadEffectRenderer` は `padRefRotationAngle` を使う。
- `TrajectoryPredictor`・`TrailRenderer` の先減算式: 大きな座標（例: 1 AU 付近）でも描画座標の誤差が小さい。

### B. 予測サンプラー・終了理由・描画
- 終了理由 6 種（`horizon`・`impact`・`breakup`・`point_budget`・`step_budget`・`no_host`）がそれぞれ設計どおりの条件で返る。`impact` イベントがあるのは `endReason === 'impact'` のときだけ。`breakup` も同様。
- `maxSimTime` は常に最終点の時刻。`no_host` は点 0・`maxSimTime` 0・`steps` 0。
- 上限: `options.maxSteps`・`options.maxPoints` に `undefined`/`null`/0/負値/`NaN`/文字列/`Infinity`/上限 ±1 を渡しても `MAX_STEPS_CAP`・`MAX_POINTS` を超えない。ステップ予算の式（0.2 ヶ月で 120,000、0.3 ヶ月で 157,788、1 ヶ月以上で 340,000）。
- 遠近点通過は厳密な符号交差（`0 → 0` では発生しない）。描画座標系での角度の上限（`MAX_ANGLE_STEP_RAD`）。燃焼境界でのサンプル。最終点の重複除去（移動量 `1e-4 m²`・時刻 `1e-6 s` の境界）。
- 座標系の切替: 軌道投入、大気上限より上で E ≥ 0、`MAX_HOST_FIXED_ALT_M` 以上のいずれかで切り替わる。直前のサンプルが `MIN_SAMPLE_DT_S` 未満なら、それを切替点にする。
- `renderTrajectory`: 切替前は地表固定系、後は慣性系で描く。飛行中は最終点の時刻の直前まで描き、直後に消す。プレビューと飛行中で同じ形。
- Worker 経路: 結果の各項目がそのまま渡る。`maxSimTime` が 0 なら 0 のまま、欠けていれば 1 年（同期経路と一致）。
- 予測用ロケットは RCS の演出状態を更新しない（`trackRcsVisualState: false`）。
- 回帰（保証 1〜5、§4.3）: Sun+Earth の 8 方位で LEO/ISS/GTO の 0.2 ヶ月と 1 ヶ月以上、深宇宙 3 ミッションの 36 ヶ月。7 天体・`SOLAR_SYSTEM`・`BINARY_SYSTEM`・`THREE_BODY` は代表構成。描画上の角度ステップ ≤ 0.15 rad、点数 ≤ 3,000、時刻の単調増加、保証 3 の切替後 1 周以上（描画上の回転量で判定）、保証 4 (a) の到達率 ≥ 99.5%、(b) は終了理由の集合だけ、保証 5 は `step_budget`/`breakup`/`impact`/`horizon` を許す（Gate 2 Iteration 9 Watchpoint）。§4.3 の表（Sun+Earth・方位 0°）の点数・最終時刻。G2-2-01・G2-2-02・G2-3-01・G2-4-01／G2-6-01 系（計算していない期間を有効と表示しない）・G2-8-01 の再発防止。

### C. RCS・ベイパーコーン・マッハ
- `_updateRcsState`: 停止ガード（ホールドダウン・衝突・破砕）、不感帯 ±0.015 rad の境界、0.08 rad 以上で連続噴射・未満でパルス、作動条件（気圧比 0.35 の境界、推力 0、分離後タイマー）、分離後の交互ダンピングの位相、点火前のアレージ（残り 1.5 s の境界）、再点火後のアレージタイマー。`trackRcsVisualState: false` では更新しない。`telemetryCache` への同期。
- `FlightComputer`: `INTERSTAGE_COAST` で順行方向に追従し、`desiredThrustAngleRad` を毎ステップ保存する。
- `RocketRenderer._computeVisualLayout`（ペイロード単体時 `±0.70 × payloadR`・`0.85 × payloadR`）、RCS ノズルの位置と噴射方向の表（設計書 §3.2-3）、LOD しきい値の境界。
- `AeroUtils`: 気温プロファイル（対流圏界面の前後、下限 180 K・上限 350 K のクランプ）、音速、マッハ数（無効入力・無大気・大気上限より上で 0）。`computeVaporConeParams` のベル関数（§4.4 の式）の 0.82・1.00・1.22 と気圧比 0.015 の境界、マッハ角の上限。`drawVaporCone` の副コーンのしきい値 0.55。
- マッハの 0 クリア（速度 0、`clearAerodynamicParameters` の基底・サブクラス）、`TM_MACH` 経由の同期、`SoundEffects` のマッハの出典（`telemetry.mach` 優先、なければ `computeMach`）。

### D. フライトプラン
- `getTriggerValue`（`time`・`alt`・`vel`・`apogee`）と `_isStepTriggered` の境界（しきい値の直前・一致・直後）。未知のトリガ・欠けた値。
- 独立アクションのラッチ: 跨いだ行のアクションをすべて 1 回だけ発行する。未到達のガイド行より後の条件成立済みの行も 1 回だけ。`hasScheduledAction`・`consumePendingActions`。`hasPendingBurnStep` が `vel` 行を認識する（G2-04）。`ORBITAL_COAST` 中もアクションを抽出する。
- 分離の保留: 2 段・3 段機で `_isCurrentStageSepDeferred`・`_isPayloadSepDeferred` の各分岐。保留中は `STG_MECO`／`ORBITAL_COAST` のまま推力 0。`executeProfileAction` の `disableStaging` ガード、`sep_stage1`・`sep_stage2`・`sep_payload` の 2 段・3 段・自走ペイロードの各経路。
- `ORBIT_ASSIST`: 介入条件の境界（高度 140 km、水平速度 4,200 m/s、遠地点 0.88 倍、E ≥ 0、円軌道目標の比 1.5）、クランプ（`v_r` −85〜+14、`γ` −0.30〜+0.45）。`targetVInfKmS` のカットオフ（ペイロード分離後は干渉しない）。
- 7 ミッションの `flightProfile` と目標値が設計書 §3.4-2 の表と一致する。深宇宙サイジング（4 機体で `burnTime ≤ 420 s`、推力の上限）。`_adaptFlightProfileForVehicle` の `vehicle = {}` 互換。`applyToLauncher` の推奨ミッション適用条件。
- UI: 6 列の表と各列の要素・選択肢、行の追加・削除、アクションの保存・復元。スライダ `max` の 3 箇所の同期。燃料種の変更で推力が下がらない（G2-05）。打上げ済みロケットと `RocketLauncher` の設定が共有参照にならない（G2-02）。
- 結合: 7 ミッションの実飛行（Worker の `PhysicsEngine`）で分離・軌道投入・カットオフが設計どおりに起きる（代表構成）。

### E. 実行時状態・保存・復元
- 復元分岐の契約: `restoredRuntimeState === true` のときだけ復元分岐に入る。通常のロールアウトとスリングショットでは入らない（G2-01）。
- `CalcRocket.getRuntimeState`／`restoreRuntimeState` と `FlightComputer.getRuntimeState`／`restoreRuntimeState`: 往復で状態が一致する。検証（時刻のクランプ `RUNTIME_RESTORE_MAX_TIME_S`、`presState` の許可リスト、圧力のクランプ、ラッチ済みのアクションだけを保留に戻す、非有限値・型違い・欠けた項目）。
- スナップショットのプロトコル: `snapshotRuntime` → `runtimeSnapshot`、`requestRuntimeSnapshot` の応答・タイムアウト（`RUNTIME_SNAPSHOT_TIMEOUT_MS`）で `null`・破棄時の解決。`Universe.captureRuntimeSnapshot`、`SaveManager.save()` の非同期経路と同期経路。
- `ObjectManager.getState`／`loadState`／`_buildRocketPayload` の全項目（設計書 §3.5-1 の表）、デブリの `debrisSubType`。読込のガード（文字列でない、JSON でない、`universe` がない・配列）。旧形式のセーブの読込。
- `InfoPanel` の `Date` 互換、`determineOptimalSubSteps` のフォールバック、削除した定数・重複定義・旧ループが存在しない（§3.5-2）。
- 結合: Worker の実エンジンで飛行 → 保存 → 読込 → 飛行継続し、保存しなかった場合とビット単位で同じ経過になる（時間型プロファイルの遠地点など、G2-07。Rev 6.11 から、全機体・各飛行段階での保存について、イベント時刻・軌道要素・Worker の全状態の完全一致で判定する、G3-1-01）。
- 真偽値の項目は、既定値と逆の値でも保存 → 転送 → 読込の往復を確かめる（既定値の往復では落とした項目を検出できない、G3-1-02）。
- 非同期のテストには個別のタイムアウトを付け、応答が来ないときに実行全体が止まらないようにする（G3-1-07。`run_all.mjs` も 1 件あたり 300 s のタイムアウトを付ける）。

### F. ヘッドレス Chrome（`testsuites/system/`）
- 構成: 依存なし。Node の `http` で `127.0.0.1` の空きポート（`listen(0)`）にリポジトリを配信し、`/usr/bin/chromium`（環境変数で変更可）を `--headless`・一時プロファイル（`os.tmpdir()` 配下に作成し終了時に削除）・`--remote-debugging-port=0` で起動し、Node 標準の `WebSocket` で CDP を操作する。`try/finally` でブラウザとサーバーを必ず止める。
- 正常系: 起動時にコンソールエラー・未処理例外がない。天体と射点を配置し、予測線が描かれる。Rocket タブの 6 列の表（選択肢・追加・削除・320px で横スクロールなし）。打上げ後にテレメトリ（高度・速度・マッハ）が更新され、多段の分離が進む。保存 → 読込で状態が戻る。
- 異常系: 不正なセーブファイル（JSON でない、`universe` がない）でアラートが出て状態が壊れない。表に不正な値（空・負値・文字列）を入れても例外が出ない。
- 境界値: 予測期間スライダの最小 0.2 ヶ月と最大 36 ヶ月、推力スライダの `max`、表の行が 0 行・1 行・多数。

### 4.4 工程 3 で見つかり、本体を修正した不具合

テストの作成中に、設計の契約を満たしていない箇所が見つかったため、本体を直した（設計書 Rev 6.10）。いずれも、修正前後でアプリの経路の予測（5 ワールド × 7 構成の結果全体）と実飛行（15 構成）の出力が一致することを確かめた。
