## 1. 原因の分析

このブランチで直した既存の不具合（設計書 §4.13）と、保存・読込の継続のずれの原因（§4.7）を、原因で分けた。約 8 割が、次の 5 つの構造上の原因のいずれかに当たる（分類は工程 3 の担当者の判断）。

| # | 構造上の原因 | 起きた不具合（設計書 §4.13 の番号ほか） | 件数（概数） |
|---|---|---|---|
| S1 | 同じ状態を主スレッドと Worker の両方が持ち、手で同期している（同じ名前のクラスが両側にあり、どちらにどの項目があるかの定義がない） | Worker にしかない項目を主スレッドが読む（19 主天体、23 (a) 破壊後の音・(c) SRB 点火、14 アナンシエーター）、最初のフレームまでの仮の値（7 LIFTOFF、8 質量、9 SRB 表示）、手で写した記録の項目漏れ（23 (b) 衝突の破片が作られない。本ブランチの退行）、詳細度ごとに別の規則（29）、保存で運び忘れた Worker の状態（§4.7 の継続の 8 つの原因）、基準天体と距離の組（26） | 約 12 |
| S2 | 物体の生存期間（生きている／破壊済みで表示だけ残る／削除済み）が状態として決まっていない。一覧に残っていることが「存在する」と「軌跡を描き終えていない」の両方を意味する | 16 カメラの対象、28 破壊のイベント、30 破壊されたロケットの選択、§4.13-31 以降（削除後もカウントダウンが続く、リセット後の遅れたフレームで破片が戻る、削除直後の保存で物体が戻る、打上げ天体の一覧に破片） | 約 7 |
| S3 | 状態番号や ID を、意味として直接書いている | 12・13 状態番号の振り直しによるずれ、21・22・25 状態の正規化と数値の直書き、24 ID 0 を「なし」と扱う、27「太陽は ID 0」 | 約 7 |
| S4 | UI の値の持ち主が決まっていない（スライダの値が保管場所を兼ねる、表示とモデルを別々に書く） | 5 ミッション変更でスライダが動かない、10・15 タブの開閉で表示が戻らない、20 実時間が 0.998 倍 | 約 4 |

### なぜ直しても出続けたか

- 同じ値を何か所でも持ち、手で同期しているため、1 か所直しても、同じ構造の別の箇所が残る。
- 設計書は「どの行をどう直すか」（行番号・確定数式）を定める書き方で、守るべき約束（どちらの値が正しいか、物体がどの状態を経るか、保存の形式）を定めていない。監査も設計書とコードの一致を確かめるため、構造の問題は表に出ない。
- 工程 3 で変異の確認と E2E を入れて探す側が厳しくなり、main の頃からあった不具合が見えるようになった面もある。
- 修正そのものが同じ構造で次の退行を生んだ。独立監査3 Iteration 2 の 2 件（設計書 §4.14-11・-12）は、同じフラグの意味の誤りを予測でだけ直して主スレッドの音声に残したもの（S1: フラグの意味と消費者の一覧がない）と、Sun でない世界の中心を作ったことで、中心が Sun の種類であることを前提にした生成器が壊れたもの（S3: 役割と種類を名前・型の前提で表す）だった。見直しでは、フラグ・役割の定義と、それを読む箇所の一覧を 1 か所に置く（C1・C4・C6）。

## 2. 見直しで定める約束（案）

それぞれの約束で、§1 の原因の種類を「構造上起きない」または「機械的に検出できる」ものにする。詳細は見直しの設計（工程 1）で決める。

| 約束 | 対象の原因 | 内容（案） |
|---|---|---|
| C1 状態の持ち主を 1 つにする | S1・S5 | 物理の状態の持ち主は Worker だけとする。毎フレームのバッファの配置、主スレッドの写し（読み取り専用）、保存項目を、同じ 1 つのスキーマから作る。主スレッドの描画・音・表示は写しだけを読む。最初のフレームの前の値もスキーマの既定値から作る |
| C2 物体の生存期間を状態にする | S2 | 生きている／破壊済み（表示だけ）／削除済みを状態として持ち、物体の一覧は用途ごとのビュー（物理・選択・保存・描画）を通してだけ使う |
| C3 通信に世代番号を付ける | S2 | リセット・読込のたびに世代を上げ、古い世代のフレーム・応答は捨てる。`feat/trajectory-fx-flightplan` は `remove`・`clear` と毎フレームの `update` に連番（`seq`・`syncSeq`）を付けたが、実行時状態のスナップショットの応答（`runtimeSnapshot`）には付けていない。保存の要求の直後に読込を行うと、古い世界の実行時状態が同じ id の新しい物体に付く可能性がある（未再現。独立監査3 Iteration 2 の Watchpoint 4）。応答も世代で照合する |
| C4 状態は列挙値、役割はフラグで表す | S3 | 状態番号は列挙値を通してだけ扱い、正規化は 1 か所にする。「世界の中心」「自動で選んだホスト」などの役割は ID で表さず、明示的なフラグで持つ |
| C5 UI の値の持ち主をモデルにする | S4 | 時間倍率・ズーム・予測期間などはモデルが持ち、スライダと表示はモデルから一方向に書く |
| C6 一覧を 1 か所にする | S1・S5 | イベントの名前の一覧（登録表）と、版番号付きの保存形式を、それぞれ 1 か所で定義する |

### 守る条件

- 物理と予測の結果は変えない。`feat/trajectory-fx-flightplan` の d2（35 構成の予測の結果全体の md5）と s2（15 構成の実飛行）、1,400 件を超える自動テストを安全網とする。
- 既存の保存ファイル（Rev 6.12 までの形式と、それ以前の形式）は読み込める。
- 見直しの設計書は、行単位の修正ではなく、上の約束（不変条件）と、それを確かめるテストの方法で書く。
