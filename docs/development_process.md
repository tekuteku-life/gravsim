# GravSim Development Process & Quality Governance

本ドキュメントは GravSim リポジトリにおける標準開発プロセス、品質ゲート、独立監査ルールを定義する。
すべての機能追加・仕様変更・不具合修正は本プロセスに従って実施する。

---

## 1. ブランチ運用ルール

1. `main` ブランチへの直接コミットを禁止する。
2. 作業開始時に必ず `main`（最新状態）から用途に応じた作業ブランチを作成する（例: `feat/<topic>`, `fix/<topic>`, `refactor/<topic>`）。
3. すべての設計・実装・テスト・監査ドキュメントの更新は作業ブランチ上で行い、全工程の独立監査通過後にマージ・統合を検討する。

---

## 2. 開発工程と4つの独立監査ゲート

開発は以下の4工程で構成され、**各工程の完了時に作業者とは独立した別エージェントによる監査**を実施する。
**独立監査エージェントが「指摘漏れなし（PASS）」を宣言しない限り、次の工程には絶対に進めない。FAIL の場合は当該工程へ差し戻し、指摘事項の修正および横展開を完了した上で再監査を受ける。**
ただし、指摘が文書のみの問題に限られる場合は「**PASS（文書指摘あり）**」としてゲートを通過し、次工程と並行して文書を修正する（§4 の 5）。

```
[工程0] ブランチ作成
   ↓
[工程1] 設計 (Design)
   ├── システム全体を見渡した「あるべき姿」の設計書を docs/design/ に作成
   └──▶ [独立監査1: 設計監査] ──(FAIL: 設計見直し・横展開)──┐
           │ (PASS)                                          │
           ▼                                                 │
[工程2] 実装 (Implementation & Static Verification) ◀────────┘
   ├── 不要コード・冗長コード・互換用不要コードの削除
   ├── 機械的チェック（構文チェック・Lint・型チェック）エラー 0 件を必須達成
   └──▶ [独立監査2: 実装監査] ──(FAIL: 修正・横展開・機械チェック再実施)──┐
           │ (PASS)                                                         │
           ▼                                                                │
[工程3] テスト追加 (Test Authoring) ◀─────────────────────────────────────┘
   ├── Unit / Integration / Regression テスト追加
   ├── ヘッドレス Chrome を用いた UI E2E テスト（testsuites/system/）の実装
   ├── 全テストに対し「正常系・異常系・境界値」を網羅
   └──▶ [独立監査3: テスト設計・実装監査] ──(FAIL: テスト追加・横展開)──┐
           │ (PASS)                                                      │
           ▼                                                             │
[工程4] テスト実施・最終確認 (Test Execution & Release Readiness) ◀─────┘
   ├── 機械的チェック、全自動テスト、ヘッドレス Chrome UI テスト実施
   ├── コードカバレッジ計測（最低 90% 以上、目標 97% 以上）
   └──▶ [独立監査4: 最終総合監査] ──(FAIL: 該当工程へ差し戻し・再検証)──┐
           │ (PASS)                                                      │
           ▼                                                             │
       [完了] ◀──────────────────────────────────────────────────────────┘
```

## 3. 各工程の実施基準

### 3.1 工程1: 設計（あるべき姿の追求）
- 現状のコード構造や一時的な仕様に引っ張られた最短・場当たり的な対処を禁止する。
- 与えられた要求に対し、データフロー・責務境界・物理整合性・UI/Worker 同期を含めシステム全体として最もクリーンで保守性の高い「あるべき姿」を設計する。
- 既存の同等処理や類似機構に波及問題がないか横断的に設計段階で精査する。

### 3.2 工程2: 実装・静的検証・不要コード削除
- **不要・冗長コードの削除**: 役割を終えた古い処理、重複メソッド、互換性維持だけのために残された未使用コードやデッドコンフィグは安全確認の上で削除する。
- **機械的チェックの義務（独立監査2の前提条件）**:
  - 構文チェック（`node --check`）
  - 静的解析 / Lint（`eslint`）
  - 型チェック（`tsc --noEmit`）
  これらすべてが **エラー 0 件** となるまで独立監査2へ進んではならない。

### 3.3 工程3: テスト追加（UIテスト＋異常系・境界値網羅）
- **ヘッドレス Chrome UI テスト**: 実際のブラウザ DOM 操作・Canvas 描画・Worker 連携を通したエンドツーエンド UI テストを `testsuites/system/` に必ず実装する。
- **3観点の必須網羅**: すべての対象機能・テストスイートについて以下を含める。
  1. **正常系**: 期待される標準ユースケースと各組み合わせの検証
  2. **異常系**: 不正値、`null`/`undefined`、範囲外入力、状態不整合、未存在ターゲット等での安全な振る舞い
  3. **境界値**: しきい値直前・一致・直後、ゼロ・負値・最大値・配列空/単一/多段、浮動小数点精度限界

### 3.4 工程4: テスト実施・カバレッジ確認
- 全テスト（Unit / Integration / Regression / System Headless Chrome UI）が skip や緩いアサーションなしで 100% パスすること。
- コードカバレッジを計測し、**最低 90% 以上（既存水準 97% 以上の維持を推奨目標）** を確認する。

## 4. 独立監査とレビュー記録（`docs/review/`）ルール

1. **独立性の担保**: 各監査（監査1〜4）は実装作業を行うメインコンテキストとは分離された独立サブエージェント（Fresh Context）を起動して実施する。監査エージェントはコードベース・差分・テスト・実行結果をゼロベースで検証し、**見落とし・設計ミス・実装漏れ・テスト不足を厳格に発見すること**を唯一の責務とする。
2. **1アップデート 1ドキュメント**: 1回のアップデートにおける全4工程の独立監査結果は、`docs/review/` 配下の **単一 Markdown ファイル**（命名規則: `docs/review/YYYY-MM-DD_<topic>.md`）に工程順・イテレーション順に追記して集約する。
3. **監査出力フォーマット**: 各監査エージェントは対象ファイルへ以下を漏れなく記録する。
   - 対象ゲート・イテレーション番号・実施日時・判定（**PASS** / **PASS（文書指摘あり）** / **FAIL**）
   - **要修正箇所（Findings / Required Fixes）**: ファイルパス・行番号・シンボル名・現象・修正方針・分類（【文書】／【実装】、§4 の 5）（指摘がある場合は必須、指摘がない PASS 時は「なし」）
   - **前ゲートの文書指摘の解消確認**: 前ゲートが「PASS（文書指摘あり）」の場合、その指摘ごとの解消状況（§4 の 5）
   - **横展開確認（Horizontal Check）**: 類似箇所の横断調査結果と水平適用の要否
   - **次工程で注意すべき点（Watchpoints for Next Phase）**: 次工程の設計・実装・テスト・運用で留意すべき事項
4. **横展開の徹底**: いずれかの監査で指摘された不具合・設計不備・テスト漏れについては、**必ずコードベース全体から同種・類似パターンを検索して横展開確認・修正**を行ってから再監査を受ける。
5. **文書のみの指摘の扱い（PASS（文書指摘あり））**: 文書の記述だけに問題がある指摘で工程全体を差し戻すと、実装・テストが正しいまま再監査が繰り返されるため、次のとおり扱う。
   1. **定義**: 次のすべてを満たす指摘を【文書】、それ以外を【実装】とする。
      - 解消に必要な変更が、`docs/` 配下の文書（設計書など。レビュー記録は監査エージェントが書くため除く）と、ソースコード中のコメント（動作と型チェックに影響しない記述。JSDoc の型注釈は除く）に限られる。
      - 実装・テスト・設定・プリセットの変更を必要としない。
      - 記述を実態に合わせて訂正しても、設計書の要求事項を満たし続ける。訂正によって要求を満たさないことが判明する場合（例: 保証の範囲を狭めると要求が満たされなくなる）は【実装】とする。
      - 例: 実測値の転記誤り、保証や記述の適用条件（ワールド・期間・方位など）の書き漏れ、改訂履歴・見出しの不整合、コードと矛盾する説明。
   2. **判定**: 監査エージェントは各指摘に分類を付ける。指摘がすべて【文書】であれば判定を「**PASS（文書指摘あり）**」とし、【実装】が 1 件でもあれば **FAIL** とする。分類に迷う場合は【実装】とする。
   3. **進め方**: 「PASS（文書指摘あり）」のゲートは通過として扱い、作業者は次工程を開始してよい。文書の修正（横展開を含む）は次工程と並行して行い、設計書の改訂履歴に指摘 ID と修正内容を記録する。次工程の作業が指摘された記述に依存する場合（例: 保証の記述からテストの期待値を作る）は、その記述を先に修正してから使う。
   4. **確認**: 修正の確認は再監査ではなく、次のゲートの監査で行う。次のゲートの監査エージェントは、前ゲートの文書指摘がすべて解消されているかを突合して記録する。未解消のもの、または修正で新たに生じた不整合は、そのゲートの指摘とする。
   5. **最終ゲート**: 独立監査4 で「PASS（文書指摘あり）」となった場合は、修正後に独立エージェントが当該指摘の解消だけを確認し（全体の再監査は不要）、その結果をレビュー記録に追記してから完了とする。
